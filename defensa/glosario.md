KPIs: cada uno con su resultado, y SE-1 ya matizado.<br><br><br>PRespuestas para el tribunal<br>¿Por qué ArgoCD y no FluxCD?<br>Elegí ArgoCD porque ofrece una interfaz y modelo de aplicaciones más adecuados para gestionar un Data Space con múltiples componentes y dependencias. El patrón App of Apps, las Sync Waves y el estado de salud por aplicación me permitían controlar el orden de despliegue y detectar fallos por componente. Flux es una alternativa válida, más ligera y muy buena para automatización pura, pero ArgoCD encajaba mejor con la necesidad de observabilidad y control del ciclo de vida.<br><br>¿Por qué FIWARE/iSHARE frente a Eclipse Dataspace Connector?<br>FIWARE me permitía construir un Data Space basado en NGSI-LD, con un Context Broker maduro y un ecosistema de componentes open source. iSHARE/DSBA encaja con el modelo de confianza federada que quería integrar. EDC es una alternativa sólida y más centrada en el conector de datos, pero el objetivo del TFM no era solo el intercambio puntual de datos, sino desplegar y operar una plataforma completa de forma reproducible con GitOps.<br><br>¿Por qué EKS y no GKE, AKS, k3s o ECS?<br>EKS porque el trabajo se centra en AWS y necesitaba un Kubernetes gestionado con integración nativa de IAM, IRSA, Secrets Manager y VPC. GKE y AKS habrían exigido adaptar la infraestructura a otro proveedor. k3s es válido para laboratorio, pero no representa un entorno cloud gestionado. ECS no es Kubernetes y limitaría la portabilidad del modelo GitOps basado en manifiestos y Helm.<br><br>¿Por qué Terraform frente a Pulumi o AWS CDK?<br>Terraform porque es el estándar de facto en Infrastructure as Code multi-cloud, con un ecosistema muy maduro de módulos, proveedores y herramientas de validación como Checkov. Además, su modelo declarativo en HCL encaja directamente con GitOps: el estado deseado se versiona y revisa en Git. Pulumi y CDK son buenas opciones, especialmente si se prioriza código general-purpose, pero no aportaban una ventaja suficiente para este caso.<br><br>¿Por qué MongoDB standalone? ¿Qué implicaciones tiene en producción?<br>Fue una decisión deliberada para el laboratorio, documentada en el ADR-003, para reducir coste y complejidad operativa. En producción no sería adecuado: MongoDB debe desplegarse como replica set de al menos tres miembros para alta disponibilidad y tolerancia a fallos. La arquitectura GitOps no cambia; solo cambia la configuración del entorno.<br><br>¿Cómo garantizas reproducibilidad real más allá de Terraform?<br>Con tres mecanismos. Primero, Terraform versiona y aprovisiona la infraestructura. Segundo, ArgoCD y Helm definen declarativamente el estado de las aplicaciones en Git. Tercero, el pipeline usa versiones inmutables del framework, no la rama principal, y aplica validaciones automáticas. Además, validé el re-despliegue tras destrucción total y la idempotencia con un nuevo terraform apply sin cambios.<br><br>¿Qué pasa si ArgoCD o Git fallan?<br>El clúster sigue ejecutando la última configuración sincronizada. GitOps gobierna el ciclo de vida y la reconciliación, no el runtime inmediato. Si Git falla, no hay cambios nuevos; si ArgoCD falla, el clúster sigue operativo, pero pierde la autocorrección y la capacidad de desplegar cambios. Por eso, en producción, ArgoCD y Git deben tener alta disponibilidad y backups.<br><br>¿Cómo escalas este laboratorio a producción multi-tenant?<br>Mantendría la misma base: Terraform para infraestructura y ArgoCD para aplicaciones, pero con separación por entornos o tenants mediante namespaces, proyectos de ArgoCD, políticas de red y cuotas de recursos. Para multi-clúster usaría ApplicationSets y GitOps por entorno. Además, añadiría autoscaling con Karpenter, MongoDB en replica set, observabilidad completa y controles de aislamiento por tenant.<br><br>¿Qué parte es contribución tuya y qué parte es integración de herramientas existentes?<br>Mi contribución es el modelo de referencia integrado: el diseño C4, el framework de 25 módulos Terraform, la estructura GitOps con App of Apps y Sync Waves, la integración de Kong como Policy Enforcement Point con la Trusted Issuers List, el pipeline seguro y la definición y medición de los KPIs. Las herramientas —Terraform, ArgoCD, FIWARE, Kong, GitHub Actions— son existentes; el aporte está en cómo las integro en un sistema completo, reproducible y auditable.<br><br>¿Cuál es la limitación más importante del trabajo?<br>La principal es que se valida en un entorno de laboratorio, con una sola réplica por componente, MongoDB standalone, dos nodos SPOT y JWT HS256 en sandbox. Eso limita la evidencia sobre alta disponibilidad, escalado real y conformidad productiva. Sin embargo, el diseño contempla la evolución a producción y el modelo es reutilizable cambiando la configuración del entorno.<br><br>¿Por qué solo 6 semanas?<br>Fue una ejecución intensiva y acotada: definí un alcance concreto, reutilicé mi experiencia previa en AWS, Kubernetes, Terraform y GitOps, y prioricé un artefacto funcional y medible. No significa que el problema sea trivial; significa que el trabajo se centró en construir y validar un modelo de referencia viable, dejando la operativa productiva como línea futura.<br><br>¿Por qué el KPI RD-1 no cumple?<br>Porque el umbral de 30 minutos era demasiado optimista para incluir la creación completa del clúster EKS. De los aproximadamente 40 minutos totales, unos 17 corresponden al aprovisionamiento inicial de EKS. El proceso GitOps posterior —validación, despliegue y reconciliación— es considerablemente más rápido. Es una limitación de definición del KPI y del coste de aprovisionamiento inicial, no del modelo GitOps.<br><br>¿Por qué HS256 en sandbox?<br>Porque en el laboratorio prioricé validar el flujo de autorización y la integración con Kong y la Trusted Issuers List de forma controlada y económica. HS256 es adecuado para pruebas sandbox, pero no para producción. En un despliegue real usaríamos certificados eIDAS y un iSHARE Satellite, con claves asimétricas y una cadena de confianza federada.<br><br>¿Por qué solo 2 nodos SPOT?<br>Por coste: era un entorno de laboratorio con presupuesto limitado. Los nodos SPOT permiten reducir coste, pero no son la opción ideal para cargas críticas. En producción usaría un pool de nodos con autoscaling, preferiblemente Karpenter, distribuido en varias zonas de disponibilidad y con tolerancias a interrupciones configuradas.<br><br>¿Qué ocurre si Git o ArgoCD caen?<br>El sistema sigue funcionando con la última configuración sincronizada. GitOps no es un componente en el camino de cada petición: es el mecanismo que declara y reconcilia el estado. La caída afecta a la capacidad de desplegar cambios y autocorregir desviaciones, no a la disponibilidad inmediata de las aplicaciones.<br><br>¿Qué aporta frente a los charts oficiales de FIWARE?<br>Los charts oficiales resuelven el despliegue de componentes, pero no proporcionan por sí solos un modelo operativo completo. Mi enfoque usa Applications independientes para tener salud, versionado y trazabilidad por componente; Sync Waves explícitas para respetar dependencias; y evita las dependencias ocultas de un Helm umbrella. Además, lo integro con Terraform, pipeline seguro, secretos, Kong e iSHARE, y lo valido con KPIs.<br><br>Respuestas extra probables<br>¿Por qué Kong y no otro API Gateway?<br>Porque Kong funciona como Policy Enforcement Point y permite validar JWT y aplicar políticas antes de que la petición llegue a Orion-LD. Es ligero, se despliega en modo DB-less y se integra bien en Kubernetes y GitOps.<br><br>¿Por qué Orion-LD y no otro Context Broker?<br>Porque Orion-LD implementa NGSI-LD, el estándar relevante para interoperabilidad semántica en los Data Spaces europeos. Es el componente central para publicar y consultar contexto de forma estandarizada.<br><br>¿Por qué GitHub Actions y no GitLab CI o Jenkins?<br>Porque el repositorio está en GitHub y Actions permite integrar validación, aprobación, OIDC y despliegue sin mantener infraestructura adicional de CI. Jenkins exigiría operar un controlador adicional; GitLab CI habría sido válido si el repositorio estuviera en GitLab.<br><br>¿Por qué OIDC en vez de claves estáticas?<br>Porque OIDC permite que GitHub Actions obtenga credenciales temporales de AWS sin almacenar secretos de larga duración. Reduce la superficie de ataque y elimina el riesgo de filtración de claves estáticas.<br><br>¿Cómo validaste la seguridad?<br>Con controles estáticos y pruebas funcionales. Checkov analiza el código Terraform, TruffleHog busca secretos expuestos y validé el comportamiento de Kong con cuatro escenarios: sin token, firma inválida, emisor no registrado y token válido.<br><br>¿Qué harías diferente si empezaras de nuevo?<br>Definiría el KPI de tiempo separando aprovisionamiento inicial de EKS del despliegue GitOps, y añadiría antes observabilidad con OpenTelemetry y pruebas automatizadas de conformidad. También exploraría antes la federación multi-clúster con ApplicationSets.<br><br>Regla para responder<br>Si te bloqueas, usa siempre esta estructura:<br><br>text<br>1. ## 3. Control de acceso (modelo XACML)

| Término | Qué es | En el TFM |
|---|---|---|
| **PEP** (Policy Enforcement Point) | Punto que intercepta la petición y aplica la decisión: deja pasar o rechaza. | **Kong** |
| **PDP** (Policy Decision Point) | Decide si una petición está permitida según las políticas. | Objetivo: Keyrock/AuthZForce (trabajo futuro). Hoy la lógica de decisión está en el plugin de Kong. |
| **PIP** (Policy Information Point) | Fuente de atributos que consulta la decisión. | La **TIL** (¿el emisor está registrado?). |
| **PAP** (Policy Administration Point) | Donde se administran las políticas. | Git (configuración declarativa de Kong). |
| **XACML** | Estándar OASIS de políticas de control de acceso basado en atributos (ABAC). | Arquitectura objetivo con Keyrock. |
| **JWT** | Token `header.payload.firma`. Claims usados: `iss` (emisor) y `exp` (expiración). | Kong verifica la firma y `exp`; `iss` se consulta en la TIL. |
| **HS256 / RS256** | HS256: HMAC con secreto compartido (simétrico). RS256: firma con clave privada y verificación con certificado (asimétrico, lo que pide iSHARE). | Laboratorio: HS256 en sandbox. |
| **OAuth2 / OIDC** | Protocolos de autorización y de identidad. | Keyrock (OAuth2) y GitHub → AWS (OIDC). |
| **Fail-closed** | Si el componente de confianza no responde, se rechaza. | TIL caída → Kong responde 503, nunca deja pasar. |
| **401 / 403 / 503** | 401: no autenticado (sin token o firma inválida). 403: autenticado pero no autorizado (emisor fuera de la TIL). 503: servicio de confianza no disponible. | Tabla 26: 401 / 401 / 403 / 200. |

## 4. Arquitectura y método

| Término | Qué es |
|---|---|

| **ADR** (Architecture Decision Record) | Registro breve de una decisión de arquitectura con contexto, opciones y consecuencias. Citados: ADR-003 (MongoDB standalone) y ADR-006 (Kong como PEP). |
| **Design Science Research (DSR)** | Metodología que construye un artefacto y lo evalúa contra métricas. Aquí el artefacto es la plataforma y los KPIs son la evaluación. |
| **Generic Enabler** | Componente reutilizable del catálogo FIWARE. |

## 5. GitOps y Kubernetes

| Término | Qué es |
|---|---|
| **GitOps** (principios OpenGitOps) | 1 Declarativo, 2 versionado e inmutable, 3 obtenido automáticamente (*pull*), 4 reconciliado de forma continua. |
| **Pull vs push** | En GitOps el clúster (ArgoCD) trae los cambios de Git; el pipeline no tiene credenciales del clúster. |
| **ArgoCD** | Operador GitOps que compara Git con el clúster y converge. |
| **Application** | Recurso de ArgoCD: un origen (repo o chart) desplegado en un destino (clúster y namespace). |
| **App of Apps** | Una Application raíz (`fiware-data-space`) que crea las demás. |
| **Sync Waves** | Orden de despliegue: −2 ClusterIssuers → −1 ClusterSecretStore → 0 ExternalSecrets + MySQL → 1 Keyrock, TIL, CCS → 2 Orion-LD + Mongo → 3 Kong. |
| **Synced / Healthy** | Synced: el clúster coincide con Git. Healthy: los recursos funcionan. |
| **Drift** | Diferencia entre el clúster y Git (por ejemplo, un `kubectl scale` manual). |
| **selfHeal / prune** | selfHeal deshace el drift; prune borra lo que ya no está en Git. |
| **Helm / chart / umbrella chart** | Gestor de paquetes de Kubernetes; un umbrella chart agrupa subcharts. |
| **Namespace** | Partición lógica: `argocd`, `trust-anchor`, `provider`, `platform`. |
| **Deployment / StatefulSet / Pod** | Formas de ejecutar contenedores; StatefulSet para cargas con identidad estable (MySQL, Keyrock). |
| **PVC / emptyDir** | PVC: volumen persistente (EBS). emptyDir: disco temporal que muere con el pod. |
| **Ingress / ingress-nginx / NLB** | Entrada HTTP(S) al clúster; NLB de AWS → ingress-nginx → servicios. |
| **Kong DB-less** | Kong sin base de datos: configuración declarativa cargada desde Git. |
| **External Secrets Operator (ESO)** | Sincroniza secretos de AWS Secrets Manager a Secrets de Kubernetes. Recursos: `ClusterSecretStore` y `ExternalSecret`. |
| **cert-manager / ClusterIssuer / ACME DNS-01** | Emite certificados Let's Encrypt; DNS-01 prueba el control del dominio con un registro TXT en Cloudflare. |
| **IRSA** | IAM Roles for Service Accounts: cada pod asume su propio rol IAM vía el OIDC del clúster EKS, sin claves. |
| **AWS Load Balancer Controller (LBC)** | Crea y gestiona los NLB/ALB desde Kubernetes. |
| **kubeconform / Helm lint** | Validan manifests y charts contra su esquema antes de desplegar. |
